Deployment

This guide takes a working Facil program to production: how to start it, how many threads to give it, how to run it under systemd or in a container, what to put in front of it, how to check its health, and how to cut its start-up time.

The server program

A production entry point is a small script. This one is used throughout the page:

using Facil

const STARTED = time()

function app(req)
    p = path(uri(req))
    p == "/health" && return Response(StatusCodes.OK, "ok")
    p == "/" && return Response(StatusCodes.OK, "up for $(round(Int, time() - STARTED)) s\n")
    Response(StatusCodes.NOT_FOUND, "not found\n")
end

# Compile the handler before the first client arrives.
app(Request(Methods.GET, "/health", ""))

host = get(ENV, "HOST", "127.0.0.1")
port = parse(Int, get(ENV, "PORT", "8080"))

serve(app, host, port;
      verbose = true,          # a start-up line on stderr with the address, threads and limits
      shutdown_grace = 20,     # seconds for requests in flight when SIGTERM arrives
      max_body_size = 1 << 20, # this service takes no large uploads
      timeout = 30)            # idle keep-alive connections are closed after 30 s

Things worth copying:

  • Address and port come from the environment, so the same file runs on your laptop, under systemd and in a container.
  • /health answers without touching anything else. Load balancers and orchestrators poll it.
  • The handler is called once before serve, so Julia compiles it before the first client arrives. See Start-up time.
  • shutdown_grace is how long requests in flight get when the process is asked to stop.
  • Limits are set for this service, not left at the general defaults. Security goes through them.

Bind to 127.0.0.1 when a reverse proxy on the same machine is the only client, and to 0.0.0.0 in a container or when clients connect directly.

Threads

julia -t 4 --gcthreads=4 --project=. server.jl
  • -t N (or JULIA_NUM_THREADS=N) sets Julia's threads, which run your task handlers. Never run a task-handler server with one thread: Facil then runs handlers inline on the event loop, and one slow handler stalls every connection (Handlers and concurrency).
    • Handlers that mostly wait (database, other services): 2 to 4 threads carry thousands of concurrent requests.
    • Handlers that compute: one thread per core you want to use, and leave a core for the reactor.
    • -t auto uses every core, which is rarely what a container with a CPU quota wants. Set the number explicitly there.
  • --gcthreads=N (or JULIA_NUM_GC_THREADS=N) sets the garbage collector's threads. With -t 1 Julia collects with a single thread and every pause is longer than it needs to be; give an inline server --gcthreads=4. With -t 4 or more Julia already uses several. Performance tuning has the measurements.
  • reactors stays at 1 unless you have measured that the event loop is the bottleneck.
Apple silicon: use one GC thread

On macOS with an Apple silicon CPU, run Julia with --gcthreads=1 (or JULIA_NUM_GC_THREADS=1). Julia's collector has a race between its threads when they sweep in parallel: rarely, a full collection releases memory that is still in use and the process crashes with a segmentation fault in gc_setmark_pool_. It was seen with Julia 1.13.4 and the code is the same in 1.12 and 1.13; it needs several GC threads and a heap of a few megabytes, and it is not specific to Facil. A script with no packages that calls GC.gc(true) in a loop crashed in 4 of 74 one-minute runs on a macOS arm64 CI machine and in none of 40 with one GC thread. Linux, on x86-64 and on ARM, did not crash in the same runs.

Facil does not fork worker processes. One process serves one port and scales with threads.

systemd

[Unit]
Description=Notes API (Facil)
After=network-online.target
Wants=network-online.target

[Service]
User=notes
WorkingDirectory=/srv/notes
Environment=HOST=127.0.0.1 PORT=8080
Environment=JULIA_NUM_THREADS=4 JULIA_NUM_GC_THREADS=4
ExecStart=/usr/local/bin/julia --project=/srv/notes /srv/notes/server.jl

# SIGTERM makes `serve` drain; give it longer than shutdown_grace.
KillSignal=SIGTERM
TimeoutStopSec=30
# 143 is how a process that drained after SIGTERM exits.
SuccessExitStatus=143
Restart=on-failure
RestartSec=2

# One file descriptor per connection.
LimitNOFILE=65536

NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/srv/notes/data

[Install]
WantedBy=multi-user.target
  • systemctl stop sends SIGTERM. serve then stops accepting, lets requests in flight finish for up to shutdown_grace seconds, and the process exits with status 143. Julia writes a signal 15: Terminated report to the journal on the way out; it is not an error. TimeoutStopSec must be longer than shutdown_grace, and SuccessExitStatus=143 tells systemd that this exit is a clean stop.
  • On Julia 1.10 and 1.11 the SIGTERM drain cannot finish handlers that are waiting on I/O (a database, another service): see Draining before the signal. There, give the service a drain endpoint and add ExecStop=/usr/bin/curl -fsS -X POST -H "X-Drain-Token: ..." http://127.0.0.1:8080/admin/drain to the unit, so that requests are drained before systemd sends the signal. Julia 1.12 and later need none of this.
  • Facil writes its own messages (start-up line, handler errors) to stderr, which systemd sends to the journal: journalctl -u notes.
  • LimitNOFILE bounds the number of open connections; each one is a file descriptor. facil.io raises the soft limit to the hard limit at start-up.

This unit file is not executed by the documentation build.

Containers

FROM julia:1.11-bookworm AS build
RUN apt-get update && apt-get install -y --no-install-recommends git build-essential zlib1g-dev ca-certificates \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /opt
RUN git clone --depth 1 https://github.com/aryan-juliahub/Facil.jl
RUN julia --project=Facil.jl -e 'using Pkg; Pkg.instantiate(); using Facil'
WORKDIR /srv/app
COPY Project.toml server.jl ./
RUN julia --project=. -e 'using Pkg; \
    Pkg.develop([PackageSpec(path="/opt/Facil.jl/lib/HttpTypes"), PackageSpec(path="/opt/Facil.jl")]); \
    Pkg.instantiate(); Pkg.precompile()'

FROM julia:1.11-bookworm
RUN useradd --system --create-home app
COPY --from=build /opt/Facil.jl /opt/Facil.jl
COPY --from=build /srv/app /srv/app
COPY --from=build /root/.julia /home/app/.julia
RUN chown -R app:app /home/app/.julia
USER app
WORKDIR /srv/app
ENV HOST=0.0.0.0 PORT=8080 JULIA_NUM_THREADS=4 JULIA_NUM_GC_THREADS=4
EXPOSE 8080
# The exec form makes julia PID 1, so `docker stop` delivers SIGTERM to it.
ENTRYPOINT ["julia", "--project=/srv/app", "/srv/app/server.jl"]
  • Use the exec form of ENTRYPOINT so that Julia is PID 1 and receives the SIGTERM that docker stop and Kubernetes send. A shell-form entry point swallows it and your requests are cut off after the stop timeout.
  • Set JULIA_NUM_THREADS explicitly to match the container's CPU limit.
  • The build stage needs a C compiler because Facil's C library is built from source for now; the final image does not.
  • Precompiling in the build stage (Pkg.precompile()) keeps that cost out of container start-up.
  • For Kubernetes, point livenessProbe and readinessProbe at /health, set terminationGracePeriodSeconds above shutdown_grace, and call your drain endpoint from a preStop hook if handlers do I/O and Julia is older than 1.12.

This Dockerfile is not built by the documentation build.

Behind a reverse proxy

Facil serves HTTPS itself (HTTPS), so a proxy is optional. Put one in front when you want HTTP/2 or HTTP/3 towards browsers (Facil speaks HTTP/1.1 only), several services on one address, or certificate management in one place.

upstream notes {
    server 127.0.0.1:8080;
    keepalive 64;                       # reuse connections to Facil
    keepalive_timeout 20s;              # below Facil's `timeout` (40 s by default)
}

server {
    listen 443 ssl;
    server_name notes.example.com;
    ssl_certificate     /etc/letsencrypt/live/notes.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/notes.example.com/privkey.pem;

    client_max_body_size 1m;            # keep in step with max_body_size

    location / {
        proxy_pass http://notes;
        proxy_http_version 1.1;         # Facil speaks HTTP/1.1; needed for keep-alive
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /ws {                      # WebSockets
        proxy_pass http://notes;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 1h;
    }

    location /events {                  # server-sent events and streamed responses
        proxy_pass http://notes;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_read_timeout 1h;
    }
}

What matters, whichever proxy you use:

  • Speak HTTP/1.1 with keep-alive to Facil. nginx defaults to HTTP/1.0 and a new connection per request, which wastes most of Facil's speed.
  • Keep the proxy's idle timeout below Facil's timeout (40 seconds by default). Otherwise Facil may close an idle connection at the moment the proxy reuses it, and the client sees a 502.
  • Pass Upgrade and Connection for WebSocket paths, and raise the read timeout: an idle WebSocket is normal.
  • Turn off response buffering for event streams and streamed responses, or events arrive in bursts.
  • Facil does not interpret X-Forwarded-For or X-Forwarded-Proto. They are ordinary headers: read them with get(headers(req), "x-forwarded-for", nothing), and only trust them when the proxy is the only way to reach the server.
  • Match body limits (client_max_body_size and max_body_size), so the client gets the same answer whichever side refuses.

Health checks and rolling restarts

  • Liveness: GET /health returning 200 shows that the event loop and a worker are alive.
  • Readiness: if your service needs something before it can answer (a database pool, a warm cache), start listening only after it is ready, or answer 503 from /health until then.
  • Draining: on SIGTERM the server stops accepting at once, so a load balancer sees connection refusals and moves on. Requests already in flight finish within shutdown_grace (on Julia 1.10 and 1.11 only if their handlers are not waiting on I/O; drain those with close(server; grace) first, see Shutdown and signals). For a load balancer that needs warning, fail /health first, wait one check interval, then stop the process.
  • Facil.connections(server) and the other counters make a metrics endpoint in a few lines.

Shutdown and signals covers the stop sequence in detail.

Start-up time

A Julia process takes longer to start than a Node.js one, and the first request to each route waits for compilation. Measured on the benchmark machine (rows 12 and 13):

Plain juliaWith a system image
Process start to first response764 ms314 ms
First request, once the server is up318 ms6.9 ms

Later requests are not affected. Three things help, in order of effort.

1. Call the handler before serving. The line app(Request(Methods.GET, "/health", "")) in the program above compiles the handler and the routes it touches before the port opens. Call it once per route that matters. It costs one line and moves the delay from the first client to start-up.

2. Precompile in your own package. If your application is a package, a PrecompileTools workload that calls the handler stores the compiled code with the package, so start-up does not pay for it either.

3. Build a system image with PackageCompiler. Split the application from the serve call so that a warm-up script can load it:

# The application, without the `serve` call, so that the server program, the
# tests and the sysimage warm-up script can all include it.
using Facil

const STARTED = time()

function app(req)
    p = path(uri(req))
    p == "/health" && return Response(StatusCodes.OK, "ok")
    p == "/" && return Response(StatusCodes.OK, "up for $(round(Int, time() - STARTED)) s\n")
    Response(StatusCodes.NOT_FOUND, "not found\n")
end

The warm-up script starts the app, sends one request per route and stops:

# Run by PackageCompiler while it builds the sysimage: start the app, send it
# one request per route so their code is compiled into the image, and stop.
using Facil
import Downloads

include(joinpath(@__DIR__, "deploy_app_routes.jl"))

server = serve!(app, "127.0.0.1", 0)
for target in ("/health", "/", "/missing")
    Downloads.request("http://127.0.0.1:$(port(server))$target"; output = devnull, throw = false)
end
close(server)
wait(server)

The build script:

# Build a system image that already contains Facil, your packages and the
# compiled code of your routes:  julia --project=. deploy_sysimage.jl
using PackageCompiler

create_sysimage([:Facil];
                sysimage_path = "app_sysimage.so",
                precompile_execution_file = joinpath(@__DIR__, "deploy_warm.jl"))
julia --project=. -e 'using Pkg; Pkg.add("PackageCompiler")'
julia --project=. deploy_sysimage.jl                           # several minutes
julia -t 4 -J app_sysimage.so --project=. server.jl

Rebuild the image whenever Facil, Julia or your dependencies change. The warm-up script runs in the documentation build; the image build itself takes minutes and was run by hand.

Memory

An idle Facil process uses about 380 MB of resident memory, most of it the Julia runtime (row 10 of the benchmarks; Node.js uses about 50 MB). Each idle keep-alive connection adds little, and an idle WebSocket about 285 bytes (row A28). Size containers accordingly: 512 MB is a sensible floor.

Windows

Facil does not run natively on Windows, because facil.io has no Windows port. Run it inside WSL2, where it is an ordinary Linux process: install Julia in the WSL distribution, follow Install there, and reach the server from Windows at localhost. HttpTypes works natively on Windows. See Platform support.

Checklist

  • julia -t N with N >= 2, set explicitly in containers
  • address and port from the environment; 127.0.0.1 behind a local proxy
  • limits set for the service (max_body_size, timeout)
  • /health endpoint, polled by whatever restarts the process
  • SIGTERM reaches Julia; the supervisor waits longer than shutdown_grace
  • a drain endpoint called before the stop signal, if handlers do I/O
  • proxy uses HTTP/1.1 keep-alive with an idle timeout below timeout
  • open-file limit above the expected number of connections
  • handler called once before serve, or a system image
