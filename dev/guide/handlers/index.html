Handlers and concurrency

This guide explains where your handler runs, what that allows it to do, and how to choose between the two handler modes. Read it before you put a Facil server under load: the choice between a task handler and an inline handler is the one decision that most affects both correctness and speed.

The threads in a Facil process

  • The reactor is the thread that runs facil.io's event loop. It owns every socket: it accepts connections, parses requests, and writes responses. There is one reactor per process by default, shared by all servers in it.
  • Julia's threads are the ones you ask for with julia -t N. Facil keeps a pool of worker tasks on them.
  • A timer thread in the C library wakes tasks that called Facil.sleep and fires timers.

Two handler modes

Task handler (inline = false, the default)Inline handler (inline = true)
Runs ona worker task, on a Julia threadthe reactor thread
May block (I/O, Facil.sleep, locks, wait)yesno: every connection on that reactor waits
Requests handled at the same timeas many as there are waiting tasks; CPU work is limited by threadsone per reactor thread
Cost per requesttwo hand-offs between threadsnone
Needsjulia -t 2 or morenothing
using Facil

# Never waits: safe to run on the reactor thread.
serve!("127.0.0.1", 8081; inline = true) do req
    Response(StatusCodes.OK, "pong")
end

# Waits (here it sleeps; in a real service, a database or another API).
serve("127.0.0.1", 8080) do req
    Facil.sleep(0.05)
    Response(StatusCodes.OK, "done on thread $(Threads.threadid())")
end

One process, two servers, one reactor: the first never waits and runs inline; the second waits 50 ms per request and runs on worker tasks. Twenty concurrent requests to the second finish in about 50 ms in total, not one second, because a sleeping task occupies no thread.

Task handlers

A task handler is ordinary Julia code. It can do anything a task can do:

using Facil

function work(req)
    p = path(uri(req))
    if p == "/wait"
        Facil.sleep(0.2)                      # waiting: fine on a worker task
    elseif p == "/compute"
        sum(sqrt(i) for i in 1:20_000_000)    # CPU work: occupies one thread
    end
    Response(StatusCodes.OK, "$(p) ran on thread $(Threads.threadid())")
end

serve(work, "127.0.0.1", 8080)
  • Waiting is free. While /wait sleeps, its worker serves other requests. You can have thousands of requests waiting on a database with a handful of threads.
  • CPU work occupies a thread. While /compute runs, one of your N threads is busy. With -t 4 at most four such requests make progress at once; the rest queue. The reactor is not affected: it keeps accepting and parsing, and inline servers in the same process keep answering.

How the pool works, precisely:

  • When a request arrives, the reactor pauses that connection and queues a job. An idle worker takes it at once; if none is idle, Facil starts a task for it. A handler does not get a fresh task per request in the common case, which is what keeps the cost low.
  • Up to Threads.nthreads(:default) - 1 workers stay alive between requests (one fewer still, nthreads(:default) - 2, when Julia has no interactive thread, which is the case on Julia 1.10 and 1.11 unless you ask for one). One thread is always left free for tasks that yielded. With julia -t 4 on Julia 1.12 or later that is three workers.
  • An idle worker waits in C, not in Julia's scheduler, so an idle server uses no CPU.
  • When the handler returns, the result is handed back to the reactor, which writes it and resumes the connection.

Facil.paused_requests() tells you how many requests are with a worker right now.

Inline handlers

An inline handler runs inside the event loop. Nothing is handed anywhere, so it is the fastest way to answer, and the only work per request is your code.

The price is a hard rule: an inline handler must not block. While it runs, the reactor does nothing else. No other request is read, no response written, no WebSocket message delivered. "Block" means anything that waits:

  • sleep, Facil.sleep, wait, fetch, take! on an empty channel;
  • reading from a socket, a database driver, an HTTP client;
  • lock on a lock that another task may hold for long;
  • reading a large file from a slow disk;
  • more than a fraction of a millisecond of computation.

Good inline handlers: health checks, lookups in an in-memory table, anything that builds a response from data already in memory.

One Julia thread means inline handlers

With julia -t 1 (the default when you pass no -t), task handlers cannot run beside the reactor, so Facil runs every handler inline whatever inline says. verbose = true prints a note when that happens. A handler that sleeps for a second then stalls the whole server for a second. Always start a server with -t 2 or more unless inline is what you want.

The same rule applies to the other callbacks that run on the reactor: before_body, Stream(on_chunk), WebSocket callbacks without spawn = true, and subscribe(f, channel) callbacks without spawn = true.

Which one to use

Start with the default. Task handlers are safe: a slow handler slows only its own request. Switch a server to inline = true when both are true:

  1. its handlers never block, and
  2. you care about the last bit of throughput, or about CPU use and latency at light load.

The measured difference, from the benchmarks (Apple M5 Pro, loopback, 100 connections; Node.js 22 for scale):

LoadInlineTaskNode.js
Tiny reply, maximum rate232,517 req/s (row A1)207,469 req/s (row A26, 4 threads)170,961 to 174,635 req/s
10,000 req/s, p99 latencynot measured0.173 ms (row 31-p99)0.142 ms
10,000 req/s, server CPUnot measured0.179 cores (row 31-cpu)0.147 cores
50,000 req/s, p99 latency0.055 ms (row A21)not measured0.061 ms

At full load the two modes are close, because the workers never go to sleep. At a light, steady load each hand-off wakes a sleeping thread, so a task-handler server uses about 20% more CPU than Node and has a slightly higher p99 (rows 31-p99 and 31-cpu are approved exceptions on the scoreboard). Inline handlers have no hand-off and are ahead of Node at every load measured.

So:

  • Handlers that never block, light load or latency-sensitive: inline = true.
  • Handlers that wait for anything: the default. Do not trade correctness for the difference above.
  • Both kinds in one service: two servers on two ports, as in the first example, or keep the default everywhere.
  • Uploads: reading a streamed body in a task handler pays the hand-off for every chunk. Use Stream(on_chunk) when the work per chunk does not block; see Request bodies and uploads.

Shared state

Task handlers run in parallel on several threads. Any data that more than one request can touch needs protection, as in any threaded program:

using Facil

const HITS = Threads.Atomic{Int}(0)          # a counter: atomic, no lock needed

const LAST_SEEN = Dict{String,Float64}()     # anything else: guard it with a lock
const LAST_SEEN_LOCK = ReentrantLock()

serve("127.0.0.1", 8080) do req
    n = Threads.atomic_add!(HITS, 1) + 1
    who = String(get(headers(req), "x-client", "anonymous"))
    lock(LAST_SEEN_LOCK) do
        LAST_SEEN[who] = time()
    end
    Response(StatusCodes.OK, "request $n")
end
  • Use Threads.Atomic for counters.
  • Use a ReentrantLock around everything else, and hold it briefly.
  • A const global that is only read (a lookup table built at start-up) needs nothing.

Inline handlers on a single reactor run one at a time, so they cannot race with each other, but they can still race with timers, tasks and spawn = true callbacks.

Reactor threads

reactors = N runs the event loop on N threads, and connections are spread over them.

using Facil

serve("127.0.0.1", 8080; inline = true, reactors = 4) do req
    Response(StatusCodes.OK, "hello from a reactor thread")
end
  • It is process-wide and fixed by the first server. A later serve! that asks for a different number throws an ArgumentError.
  • It helps when the reactor itself is the bottleneck: inline handlers that do real CPU work. A CPU-bound inline handler measured 17,128 req/s on one reactor, 35,731 on two, 69,330 on four and 125,898 on eight (rows A6, A7, A8 and 1).
  • It does not help handlers that are already as cheap as a tiny reply (rows 2 and 3 are no faster than row A1), and it does nothing for task handlers, which scale with -t instead.
  • HTTPS needs reactors = 1.
  • With several reactors, inline handlers do run in parallel: protect shared state.

Garbage collection

Julia's garbage collector stops every thread while it runs, the reactor included. Requests that arrive during a collection wait for it. Short collections are invisible; long ones are the slowest requests you will see. Performance tuning shows how to keep them short.

A client that goes away

Facil does not notice a client that disconnects while its handler is running. The handler runs to the end and its result is discarded. There is no cancellation. If a handler is expensive and clients are impatient, check a deadline of your own inside it. Streamed responses are different: ResponseStream reports a gone client through isopen and by throwing from write.
